Part I · Orientation
01

What the broker does

The broker authorizes agent requests and calls company systems using stored credentials.

Coding agent workflows benefit from access to company systems so they can gather relevant context, carry out related tasks and use feedback to improve their work. This supports more automation across the workflow, closes the loop between changes and their validation, and reduces manual coordination between tools.

The Agent Access Broker provides controlled access for these workflows. Giving an agent a personal access token places a long-lived credential in the workload. The broker keeps backend credentials outside the workload and provides a common place to authorize and audit agent requests, with controls over which actions are allowed from each execution environment.

An agent calls the Agent Access Broker with a typed action, such as jira.issue.view or gitlab.merge_request.create. The broker identifies the user and execution context, checks company policy, and performs authorized actions using a stored backend credential. It returns the result to the agent without exposing the credential.

Policy enforcement. The broker controls which resources agents may access, from which environments, and with which actions. Upstream systems independently enforce the permissions of the credential used for each request. A request must satisfy both sets of controls. Section 10 describes how they combine.
Request authorization
  1. Caller identity§05–06A principal: the user behind the agent, established by the platform or by a broker token.
  2. Execution environment§04An execution context such as internal or external, set by trusted infrastructure.
  3. Requested operation§03A typed action on an upstream resource: a repository, project, space or job.
  4. Access policy§08–09A grant must cover the principal, action, resource and context.
  5. Backend credential§07A stored credential: the user's own, or a configured service account.
02

Architecture at a glance

The Broker authorizes actions and holds credentials; optional trusted ingress can attest identity and context.

The Access Broker can operate independently with ordinary Broker-token and browser authentication. The optional deployment shown below adds a managed environment and trusted ingress that verifies identity and attests platform-assigned execution context. An egress policy proxy can also govern traffic to other services; those network controls are configured outside the Broker. For brokered requests, the Access Broker makes the action-level access decision and holds the credentials, while the upstream systems do the actual work. People use the broker's portal separately to sign in, register credentials and manage policy.

1

Platform-declared identity

In this deployment, trusted platform infrastructure associates a request with the user's identity bearer and an approved execution context. The transport and identity-verification mechanism belong to that infrastructure. Keep identity secrets and caller credentials outside workloads; agents cannot select the Broker's trusted context.

2

Identity forwarding

For broker-bound requests, identity-aware ingress must verify the bearer and replace untrusted assertion headers. It forwards the approved context, a SHA-256 fingerprint registered in Broker's user inventory, and its private caller credential. The raw identity bearer is not forwarded to the Broker. A basic reverse proxy does not supply this identity-verification capability automatically.

3

Unmanaged clients

Tools outside a managed environment present a self-issued agent_invoke token. Direct clients use the configured Broker default context. A configured trusted caller may instead supply an approved assertion or use Broker-fixed context.

4

Brokered execution

After authorization, the broker decrypts the user's credential (or a configured service credential) in memory and calls the upstream system. It returns the normalized result to the agent.

5

Portal

People reach the portal from the browser and sign in using configured local-password or Microsoft Entra ID authentication. Users register backend credentials and issue tokens; administrators curate resources, contexts and grants.

03

How agents connect

Agents can discover and invoke typed actions through four interfaces.

Each broker provider exposes a defined set of actions, such as view, search, create, update and trigger, with input and output schemas owned by the broker. An agent discovers which services, resources and actions are available to it, then invokes an action by name. All four interfaces use the same catalog, identity checks and policy checks.

Discovery also checks local execution and lookup credentials. Missing or unusable credentials hide affected actions, schemas and resources, including native MCP tools. An authorized service retains an availability status and setup requirements. Discovery does not contact upstream or refresh OAuth; refresh the tool list or reconnect after credentials change. Management and setup remain available.

  • Discovery. The broker filters service, resource and action listings by the caller's identity, context and policy. Each invocation is authorized separately.
  • Service connections. Select one service per client connection to expose raw provider names without a broker prefix. Current grants, backend credentials, rate limits and audit still apply. A connection view does not narrow the token itself.
  • MCP transports. The stdio server runs beside the agent and supports JSON input and output, file references for uploads and downloads, and saving read or write responses locally. A local save failure is reported separately from confirmed operation success, without replaying the operation. The HTTP endpoint serves remote clients and supports JSON input and output only.
  • Authentication. All four interfaces use platform-attached identity in managed environments and an agent_invoke token for unmanaged clients.
  • Git credentials. Unmanaged clients use a Git credential helper to supply the broker token. Managed clients use platform-attached identity. The broker supplies the GitLab credential for upstream requests.

Imported services

Base administrators can connect an upstream MCP HTTP server, import an OpenAPI document, or import a local command the operator approved, and review its operations as ordinary broker actions. This is a general integration model: agents use the same CLI, HTTP API and MCP interfaces, and calls receive the same identity, context, grant, credential, rate-limit and audit checks as built-in actions.

Configuration and ownership

  • Operator gates. TOML enables imports, selects allowed kinds, exact destinations and approved local commands, and can disable individual imported services. Removing permission stops discovery and execution while retaining definitions and grants.
  • Database catalog. Service definitions, accepted actions and encrypted shared tokens are database-managed. Startup loads the accepted catalog locally without contacting the upstream.
  • Administrator roles. Base administrators manage import definitions, review and shared tokens. They can assign service managers to the imported service to manage its grants. That role does not grant import-administration or credential-management rights.
  • Credential choices. A service enables shared tokens, personal tokens or a supported personal OAuth connection. Grants select a permitted ownership mode. A missing personal credential never falls back to a shared credential.

Review and refresh

  • Action names. Suggested identifiers can be edited before acceptance. Accepted identifiers stay fixed because agent calls and grants reference them. Retiring an action does not transfer its grants to a replacement.
  • Labels and descriptions. Optional labels default to the MCP tool title or OpenAPI summary/operation ID; administrators can edit or clear them during review. Labels appear only in the management UI. Agents receive the description and input schema. When an OpenAPI description is absent, discovery uses the upstream summary, operation ID, or HTTP method and path. Editing a label does not change that description.
  • Effects. New and changed tools start write-capable until reviewed. Upstream read-only hints are suggestions. The flag helps select grant actions and limits read-only identity paths to reads; it does not restrict the upstream operation or automatically change existing grants. Reclassifying a granted action requires confirmation.
  • Manual refresh. New tools remain unselected. A complete refresh quarantines missing, unsupported or behaviorally changed tools. Acceptance of changes affecting existing grants requires confirmation; failed discovery publishes no partial catalog.

Whole-action access. MCP and OpenAPI describe operation arguments, but provide no standard mapping to the broker's resource catalog. Those imports therefore grant whole actions, subject to upstream permissions. A local command may declare resource types: the broker checks actions that name their resources in typed inputs before the command starts, and passes the caller's grants to the command for the rest, which it must enforce itself. To enforce project, space or repository limits within the broker otherwise, implement a provider in code instead of importing.

The broker does not host upstream MCP stdio servers; a local command import runs one trusted process per call. Commands can declare single-file downloads when the operator enables a byte cap; the CLI and local stdio MCP save verified bytes and return metadata receipts. HTTP MCP exposes download detail but excludes executable download tools. The current OpenAPI / Swagger profile supports bounded JSON responses with JSON and scalar form requests; file transfers are outside that profile. No import adapter automatically replays a failed write. See import administration, OpenAPI support, command imports and OAuth connections.

Part II · Identity and context
04

Execution contexts

The execution context determines which resources are eligible for access from an environment.

Every request carries exactly one execution context, a short label for the environment the agent is running in. The context is never chosen by the agent or the client. An asserted trusted caller supplies a context from its approved set. For a fixed caller, Broker supplies its configured context and rejects a context header. Header-free direct clients use Broker's configured default or fail when context is required; omitting the execution-context section retains the built-in default. Context names and their deployment meanings are operator-defined.

ContextAssigned byEnvironmentIntended exposure
internalPlatform, per managed environmentManaged container or VM restricted to company-hosted modelsMay receive resources cleared only for internal use
externalPlatform, per managed environmentManaged container or VM that uses external model providersOnly resources cleared for sharing with external providers
workstationBroker direct default or configured trusted callerUser-configured tools such as Cursor or a local CLIOnly resources explicitly made eligible for workstation use

Where the context is enforced

  • Resource eligibility. Each catalog resource lists its permitted contexts. A grant cannot authorize access to a resource in a context where that resource is ineligible.
  • Grant contexts. Each grant lists the contexts where it applies. A grant limited to internal does not apply in external.
  • Token contexts. Issued invocation tokens name their permitted contexts. A token limited to internal is rejected when the resolved context is workstation.
  • Git access. Clone and push operations through the broker's Git gateway use the same context checks. A repository restricted to internal cannot be cloned from an external environment.

05

Managed identity path

In this optional managed deployment, identity secrets stay outside the workload. Identity-aware ingress verifies the bearer; Broker holds the upstream credential.

A

Identity provisioning

For fingerprint identity, the platform holds a per-user bearer outside the workload and Broker registers it against the human's principal. Administrators can generate, import or remove inventory. HTTP MCP can instead use an explicit namespace/username binding with no inventory. One Identity access pause gates both methods while leaving issued Broker tokens and browser sign-in available. The identity token and each binding can also be disabled or made read-only on their own.

B

Proxy authentication

Broker accepts context and fingerprint only with an authorized private caller credential. The selected ingress must strip untrusted assertions before injecting verified values. Broker validates assertions and rejects unauthenticated copies. The canonical identity header is X-AW-Identity-Token-SHA256; it does not require a particular ingress product. An explicit Broker token remains authoritative, including when invalid.

C

Managed identity permissions

Managed fingerprints support the existing discovery, invocation, MCP and Git surfaces. Trusted usernames are limited to HTTP MCP. Both apply current human permissions and grant no self-service or administration. A read-only path lists and runs only actions classified as reads, within those permissions, and cannot push with Git. MCP pins identity through final admission; identity changes reject old sessions but do not cancel operations already admitted.

06

Unmanaged clients and tokens

Clients authenticate with a user-issued Broker token. Direct clients use the configured default context; the illustrated path uses optional trusted ingress.

Token classes

ClassPrefixPurpose
agent_invokeaab_ai_Discovery, invocation, MCP and Git. Issued to agents and tools.
user_manageaab_um_Self-service: credentials and tokens. Backs portal sessions.
adminaab_ad_Administration; human admins can read/write, auditors can read. Role changes revoke these tokens.

Token properties

  • Access restrictions. Token restrictions limit access within the user's grants. They cannot authorize access beyond those grants.
  • Expiration and revocation. Self-issued tokens expire, with a 30-day maximum by default. Tokens can be paused, resumed or revoked at any time. Revocation blocks new admissions; already prepared operations may finish; uploads have a bounded receive deadline.
  • Token storage. The broker stores a keyed hash of each token. The raw token value is displayed once when issued.
  • Policy updates. Changes to grants and resources apply to existing tokens on the next request. A token's own restrictions are fixed when it is issued.
Part III · Credentials and policy
07

Sign-in and credentials

Users register tokens or connect upstream accounts through the portal. Backend authorization is separate from signing in to the broker.

Microsoft Entra sign-in

  • Sign-in protocol. The portal uses a single-tenant OIDC authorization code flow with PKCE and nonce. Accounts are identified by tenant and object ID rather than email.
  • Independent login methods. Microsoft linking preserves an existing local password. Administrators explicitly enable local password sign-in; reset only changes an active local password. Microsoft-only accounts have no Broker password to manage.
  • User provisioning. A user record is created on first sign-in only when a group claim maps to a managed group. Group evidence from Microsoft expires after eight hours unless refreshed by a new sign-in or, when membership renewal is enabled, renewed on demand from the refresh token stored at the last sign-in while the person or their agents use the broker.
  • Local onboarding groups. Administrators can automatically add newly created Microsoft users to selected active groups. This requires the same mapped-group admission and creates persistent local memberships, which survive Microsoft evidence expiry. Existing accounts are not backfilled or re-added on later sign-ins.
  • Account roles. Each account has one role: user, auditor, service policy manager, or admin. Auditors can inspect administrative metadata without changing it or revealing secrets. Roles and direct service assignments cannot be assigned through Microsoft group membership. A separate self-service flag controls personal management and My access; invocation grants remain independent.
  • Browser session permissions. Browser sessions authorize self-service operations, with CSRF and same-origin checks. They cannot authorize agent invocation.

Backend credentials

Users can paste a supported upstream token or connect an account through OAuth. Gmail has a Google OAuth adapter; GitLab REST and GitLab Git gateways share one GitLab OAuth connection per instance; Jira and Confluence use an Atlassian adapter through the Atlassian gateway; imported MCP services can use the standard MCP OAuth adapter described below. Browser sign-in with Microsoft does not itself provide an upstream API credential.

  • Token permissions. Users can limit a token to specific projects or read-only access. Agent requests must be allowed by both the token's permissions and the broker's grants.
  • Personal credentials. The broker selects the invoking user's token or OAuth connection for the configured service binding.
  • Shared credentials. Built-in providers use their configured credential source. Imported shared tokens are stored encrypted in the managed database and administered through Imports. The broker still authorizes and audits the invoking user; the upstream sees the shared credential's identity.
  • Credential storage. Credentials are encrypted and bound to their owner, service, profile and key ID. Changes to the encrypted data or these bindings cause validation to fail.

Connecting an upstream account with OAuth

Personal OAuth setup requires enabled self-service, a credential connection with OAuth and an active per_user action grant on a service that uses it, for the user or their current groups. Setup can precede usable resources or execution contexts; each invocation still needs its own authorization. Owners can inspect and disconnect an existing bound connection after grant removal. Ending a GitLab connection, by disconnect, reconnect or disabling its owner, also revokes its tokens in GitLab, and the connection reports whether that succeeded.

Authentication adapters implement the provider's OAuth behavior. The generic mcp_oauth adapter supports compatible MCP servers without new provider code. It requires an operator-approved client registration, the exact MCP endpoint/resource and a permission profile. Profiles use explicit scopes by default, or operator-selected server_default permissions with configured scopes absent. Importing tools alone does not establish a connection. Unusual provider flows still need a compiled adapter.

Setup and discovery

  • Operator registration. Register the broker with the upstream authorization server and configure the client, callback, approved metadata endpoints, OAuth resource URL (the MCP endpoint) and permission profiles in TOML. Automatic client registration is not implemented.
  • Import binding. A base administrator selects Personal credentials, OAuth, and the approved registration/profile for that exact MCP endpoint. Shared OAuth and client-credentials grants are not supported.
  • Connection owner. Users connect their own accounts in Credentials. An administrator selected for personal discovery can connect from the draft before tools or grants exist. A separate supported static discovery token is another option.

Use and lifecycle

  • Refresh and reconnect. The broker refreshes an expiring token when a refresh token is available. Access-only connections require reconnecting after expiry. An uncertain refresh also requires reconnecting.
  • Exact binding. Consent, callbacks and token use are checked against the approved issuer, MCP endpoint URL, connection and current service configuration. Credentials are never silently switched to another account or a shared token.
  • Identity and failures. Standard MCP OAuth may not identify the upstream account. The UI reports that limitation and requires confirmation when replacing it. An upstream 401 does not replay the tool call.

OAuth is implemented for Gmail, for GitLab REST and GitLab Git gateways sharing one GitLab OAuth connection, and for compatible imported MCP services. OpenAPI and Swagger imports support static Basic, Bearer and header API-key credentials; OAuth security schemes are not supported. See delegated connections, GitLab OAuth setup and MCP OAuth configuration.

08

Resources and grants

The resource catalog defines eligible targets. Grants authorize users and groups to perform actions on those targets.

For resource-scoped providers, administrators register upstream resources in a catalog and give each one the execution contexts it may appear in. Grants then select from that catalog. Access is never inferred from upstream visibility alone. A resource must be covered by an enabled catalog entry eligible for the current context and by a grant.

Imported services use action/context grants without resource selections. Their upstream credentials supply any repository or data restrictions; the importer does not derive those restrictions from tool inputs.

  • Grant coverage. For ordinary resource-scoped actions, a single grant must cover every target in a request. Native searches combine the winning grant band's clauses, narrowed by the token's resource boundary.
  • Grant selection. Direct user grants take precedence over group grants. Priority determines selection within that category. If the highest-ranked grants are ambiguous, the request is denied.
  • Search scope. Jira and Confluence constrain JQL/CQL queries upstream and check each returned item. GitLab discovery and content search confirm current repository ownership with the selected execution credential and discard unauthorized candidates before results, audit, or continuations.
  • Grant and resource status. Grants and resources can be enabled or disabled but do not expire. Time-based access restrictions come from token expiration and the validity period of group evidence.

Service managers, such as Confluence administrators, manage grants for their service. Global administrators maintain the resource catalog and each resource's eligible contexts. A delegated manager can select resources from that catalog but cannot add resources or change their context eligibility.

Delegation scope. Service managers can grant access to themselves and others, including use of a service credential. These grants remain subject to the global catalog and context eligibility. A manager must have an applicable grant to invoke an action; the management role alone does not authorize invocation.

Assignments are direct to accounts with the service policy manager role, never to groups. The current role and assignments are re-evaluated on every management request. Auditors may inspect global administrative metadata and safe previews without changing state or revealing secrets. Self-service is a separate account setting.

How a request is decided

The controls from the previous sections combine into one decision, evaluated in a fixed order for every request.

A request must satisfy each applicable control. Context eligibility determines which resources are available in the execution environment. A grant must authorize the caller's action on those resources, and any token restrictions must also permit it. The upstream system then enforces the permissions of the credential the broker presents. Broker authorization cannot override those upstream permissions.

Evaluation order

Every invocation uses the same ordered checks. If a required check fails, the broker rejects the request. Authorization must complete before the requested action executes upstream; any preliminary lookup is limited as described below.

5

Target resolution

Some requests require an upstream lookup to identify the target resource, such as the project containing an issue. The broker uses a read-only lookup credential or the caller's own credential, and performs the lookup only when a grant could apply. Error responses do not disclose the resolved target.

6

Decision records

The broker records the matched grant, its version and the policy generation with the request, identifying the policy used to authorize it.

G

Git authorization

Clone and push map to repo.fetch and repo.push on the repository's catalog entry. Pushes are also checked against ref rules: no deletions, no tags, and configured deny patterns.

Rate limits and audit

Per-service invocation limits and concurrency caps control load. Audit records capture authorization decisions, execution outcomes, and the few request inputs each action opts in, such as its project, issue or query.

Rate limiting

LimitCounted per
Service invocationsOne principal on one service, across that principal's tokens, clients and source addresses
Login attemptsOne user from one source address (local password sign-in and password change)
Authentication trafficOne source address: sign-in attempts and requests that fail authentication
ConcurrencyShared request slots held by one principal, including rate waiters
ConcurrencyShared request slots held across the broker instance, including rate waiters
  • What counts. Only requests that invoke a backend: POST /v1/invoke, MCP action tool calls and Git pack requests (a protocol v2 fetch or clone sends two or more). Discovery, specs, management and MCP protocol traffic are not counted, and each request counts once however many upstream calls it makes.
  • Limit values. Configuration sets a default and optional per-service limits. Administrators can override one principal's limit for a service in the portal, CLI or admin API, and users see their own limits on their Account page. Changing tokens or machines does not reset a principal's allowance; principals behind one proxy address are counted separately.
  • Waiting and discovery. Optional max_wait holds a request in FIFO order within existing request capacity; the default is immediate refusal. Service describe reports the caller's effective rate, pending count and estimated next admission without reserving capacity. Its separate bounded capacity remains available when invocation slots fill. Client timeouts can leave requests queued or executing; reconcile a mutation before resubmitting it.
  • Rejections. A rate-limited request is not executed. The broker returns 429 rate_limited with Retry-After, the limit and an estimated retry time after accepted waiters, so agents wait without duplicating pending calls; the CLI exits with code 7. Throttling by an upstream service is reported separately as upstream_rate_limited with the upstream's wait, except after a write has already been applied, which is reported as an unverified write that must not be retried.
  • Login protection. Failed local passwords lock a user out from one source address (IPv6 grouped by /64) for the lockout period without affecting other addresses. Beyond 256 failing addresses for one user, further addresses share a single counter.
  • Counter scope. Counters are maintained per broker instance and are not shared across replicas. Invocation limits use a rolling window; authentication limits use fixed 60-second windows.

Audit

  • Audit fields. Each outcome record includes a unique record ID (auditId), the node ID of the broker that wrote it (nodeId), the principal, groups, optional trusted caller ID (callerId), service, action, resolved resources, execution context, matched grant, credential mode, decision and upstream status. Caller ID names the attesting service and never contains credentials. Rate-limit rejections also record the limit and retry time.
  • Audit storage. Operators choose a standalone SQLite audit database, which can be searched, or size-rotated JSONL files for log shippers. Both keep records for the configured retention period.
  • Audit availability. Mandatory audit admission fails before execution or store changes when its record cannot be written. Password changes, authenticated logout, and resource or resource-group mutations persist a preflight first. If their supplemental completion record fails after commit, the response preserves the completed change and normal cookie handling, while the broker reports the audit fault through readiness and a correlated service-log event. The managed and audit stores commit separately, so a process crash can leave only preflight evidence.
  • Streaming and Git records. Streams and Git transfers write a start record before any credential is sent and a final record at completion.
  • Viewing audit. With SQLite storage, administrators and auditors see every record, service managers see records for their directly assigned services, and users with self-service enabled see their own activity, in the portal and the CLI. Agent tokens cannot read audit records.
  • Resource history. Completed resource and group changes record safe names, before/after state, and included/excluded membership changes. The portal preserves those historical labels and lets authorized catalog readers open current objects. An allowed preflight represents an attempt, not proof of completion.
  • Management reads. Successful read-only management calls, such as portal page loads and audit queries, write no audit record, so they keep working when audit writes fail. Their denials and failures, all changes, secret reveals, policy exports and credential verification are audited.
  • Secret redaction. Audit output excludes secrets and credential material.

Glossary

Identity attestation
A configured caller supplies an exact bound username on HTTP MCP or a verified registered fingerprint on supported invocation surfaces. Broker authenticates the caller, resolves the human, checks the shared identity-access gate and the path's own Enabled and Read-only settings, and applies current policy.
Trusted caller
A named infrastructure caller with its own credential, fixed or asserted context permissions, and optional managed-identity forwarding. Its credential does not authenticate the principal or add grants.
Trusted ingress
An optional infrastructure caller implementing Broker's credential and context contract, with identity forwarding only when explicitly permitted. Client-address forwarding is configured separately.
Execution context
An authorization label (internal, external, workstation) asserted by an authenticated trusted caller or fixed by Broker configuration. Header-free direct clients use the configured default.
Principal
A broker user or service account. Every identity path resolves to one.
Action
A typed, named operation a provider exposes, such as jira.issue.view. Imported action schemas are reviewed and stored in the broker catalog.
Imported service
A database-managed MCP or OpenAPI integration whose reviewed operations become broker actions, subject to operator configuration and ordinary action/context grants.
Managed identity
An explicit namespace/username binding or registered fingerprint resolves to an active human with unpaused identity access. Invocation-only; usernames are HTTP MCP only.
agent_invoke token
A broker token issued by or for a user for agent use outside managed environments. Scoped by context and optionally by service and resource.
Resource / resource group
A catalog entry for an upstream repository, project, space or job, with its eligible contexts. Groups bundle entries with inclusions and exclusions.
Grant
Policy allowing subjects to perform actions for one service in listed contexts, using a permitted credential mode and resource selections where the provider supports them.
Credential mode
per_user uses the caller's credential for the service's credential connection: a stored token or, for people where configured, an OAuth connection. service uses a shared credential; imported shared tokens are encrypted in the database.
Credential connection
One per-principal credential that one or more services use, such as one GitLab token for GitLab REST and Git. The administrator configures its method; grants stay per service.
OAuth connection
A user's consent for the broker to access an upstream service through an approved authentication adapter. Separate from browser sign-in and broker agent tokens.
Service policy manager
An account with the service policy manager role, directly assigned to manage grants for one or more services. Groups cannot hold these assignments.
Lookup credential
A read-only credential used only to resolve a target's scope before authorization.
